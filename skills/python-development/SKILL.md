# Python 函数式写法偏好

本文记录一种偏函数式的 Python 写法。重点不是完整工程规范，而是如何通过代码组织保持清晰的业务主线。Python 脚本应优先使用 Python 3.14 下可直接运行的标准语法和标准库能力，不为 3.13 及更低版本保留兼容分支或旧式写法。

## 主线

- 代码整体倾向采用流水线式组织：输入进入主线，经过一组明确变换，然后汇聚为结果。
- 多步骤数据变换通常优先用 `toolz.curried as T` 和 `T.pipe(...)` 表达。
- 分散动作应尽快汇聚，避免中间结果长期游离于主流程。
- 主线中流动的数据形态应尽量稳定；不要为了提前取出局部字段而破坏元素同质性，通常应先汇聚同类结构，再在统一边界提取、展开或转换。
- 非主线逻辑尽量放在前置检查里；常见形式是 `if` 后提前 `return`，或直接使用 `assert` 表达必须成立的前提。
- `if` 只在逻辑上严格成立“如果、那么”时才能用，`if/else` 只在逻辑上严格成立“如果、那么、否则”时才能用；只要不是严格的二分就不能用 `if` 表达，固定枚举路由、来源选择、处理器选择等应优先用局部字典分派或模式匹配，不要因为当前枚举只有两类就把路由写成 `if/else`。

## 函数与命名

- 函数保持短小，名称表达它在流水线里的角色。
- 一个函数优先只做一件事：转换一个值、组合一组结果、保存一个产物、执行一个明确副作用。
- 每个业务函数都应有简明的函数说明，用来标明业务角色或输出契约；不要机械删除有信息量的说明。
- 代码应短小精干，优先用更少的行数表达同等清晰的逻辑；每一行、每一句都应有确定作用，但不为压缩行数牺牲可读性。
- 准确命名如果会导致变量名过长，或变量只在局部使用一次，可以不为命名而引入中间变量；但能标明业务阶段、聚合结果或让条件更清楚的中间名应保留。
- 代码鼓励高级表达；能实质性减少代码且不削弱主线时，优先使用 Python 新语法和语法糖，例如海象运算符。高级表达必须让代码更短且更清楚，不为使用语法糖或管道而替换更自然的命名步骤。
- 没有实际作用的代码应清理。删除后不影响行为的代码，应删除，或改成 `assert` 等形式弱化为约束表达。
- 已由调用方或上游契约保证的必选输入，后续逻辑应直接使用；不要用 `isinstance`、`.get(..., default)`、白名单过滤等防御式写法跳过坏输入。可选字段用 `.get(...)` 表达更短更清楚时可以使用。需要表达当前业务函数真正依赖的前提时使用 `assert`，否则让异常直接暴露；不要为了“更严”增加当前逻辑不需要的额外约束。
- 参数、模板和上下文应放在真实拥有该决策的函数附近：调用方真正要决策的任务输入才进入公开函数签名；默认分页粒度、请求超时、限速节奏、请求模板等实现细节应下沉到实际使用它们的 helper 或局部函数默认值里。
- 只有跨任务共享且稳定的业务事实才适合提升为模块常量；单个接口、单个数据源或单个任务专属的模板、上下文和参数不要过早全局化。
- 多个数据源、提供方或协议边界处在同一生态位时，函数名必须体现来源边界；除真正公共 helper 和跨来源聚合入口外，不要用不带来源的泛化名字承载某个具体来源的实现。
- 已有公开函数的返回契约不要轻易改写；当需求变成另一种视图或另一种返回形态时，优先新增命名清楚的接口，让旧契约继续稳定。

## 注释

- 核心流程、主要代码块和不容易从语法本身看出的业务取舍，应补充思路性注释，说明相关逻辑的存在理由和当前写法的取舍依据。
- 注释应补充代码无法直接表达的业务约束、边界条件、流程意图或实现权衡；避免仅复述代码字面含义的说明性注释。
- 注释应保持简洁，优先服务于读者理解主线和关键决策，避免为每一行代码机械配注。

## 管道写法

- `T.pipe(...)` 是主要组织方式，适合表达一条连续业务流；不要把管道写法当作目的。
- 字段提取、属性提取、映射、筛选、组合和聚合等常见步骤，优先使用 Toolz 或标准库函数式 helper；内联 `lambda` 只在其他方式都不优雅时使用，也不为替代一行 `lambda` 生造函数。
- 当序列元素天然是 `(key, value)`、多字段元组或其他可解包结构时，函数签名应尽量直接表达这些参数；必要时用 `itertools.starmap` 等标准 helper 承接，而不是在函数体里反复拆一个泛化的 `item`。
- 读取元组中的局部信息时优先用解包表达意图；不使用的成员用 `_` 承接，避免用位置索引掩盖结构语义。
- `@T.curry` 适合把普通函数改造成可部分应用、可纳入管道的函数；当组合任务需要共享 session、事务或上下文时，可先绑定上下文形成更窄的语义函数，再交给 `map` 或局部分派器。
- `T.cons(...)` 适合把已取得的首个元素拼回后续序列，使后续 `T.map(...)`、`T.concat` 等步骤继续面向统一结构。
- `T.do(...)` 只适合承载轻量级副作用，例如日志、等待或触发一个必须发生的动作；它应放在副作用真正发生的粒度上，逐项副作用应进入逐项映射。
- 尽量延迟求值，让数据在管道中保持惰性传递。
- `list(...)` 可以作为惰性管道的显式求值边界，但应尽量推迟到必要边界；通常只在汇聚结果、触发副作用、复用结果或外部接口需要具体容器时使用。

## 数据对齐

- 跨来源合并字段前必须先确认语义，不要只因为字段名、格式或样例位置相似就认定它们等价。
- 标准列应作为面向分析的派生视图列；原始字段应保留以便追溯、复核和发现误配。
- 同名或近名字段如果单位、时点、口径、编码或生命周期不同，应拆成不同标准列，或明确转换后再合并。
- 字段转换只放在语义已经确认的边界上；无法确认的字段宁可保留原样，也不要为了表面整齐强行合并。

## 接口抓取

- 需要复用连接状态时，用上下文协议封装会话生命周期，并在会话创建后一次性写入稳定上下文；单次请求函数只表达如何发送请求和处理基础响应。
- 请求 helper 只表达通用发送动作，例如 `get_json(session, url, params=None, timeout=...)` 或 `post_json(...)`；查询参数用结构化 `params`，不要手拼 `&`，但稳定请求上下文应写入 session，不要在公共 helper 上开口子。
- 接口专属的地址、请求头、请求体模板和业务参数应留在接口局部；外层批量任务只暴露调用方真正需要决策的任务级参数。默认分页粒度属于具体分页请求函数，限速等待属于分页循环，请求超时属于请求 helper，不应一路透传到高层业务入口。
- 如果首个响应承担发现分页、总量或后续范围的职责，应在首个响应后就近校验这些勾稽关系；后续响应只校验后续流程真正依赖的成功契约。
- 不要把所有 `assert` 机械抽成独立函数；只有跨接口复用的契约才值得抽象，局部契约就近表达更清楚。
- 当已有函数已经表达稳定业务动作时，组合任务应优先复用这些语义函数；只有为了共享会话、事务或缓存等生命周期时，才补充显式上下文 helper，不要让组合任务越过业务封装直接操作底层请求。
- 需要在组合任务中共享上下文时，可把公开函数整理成薄包装和显式上下文 helper：公开函数保持易用，helper 接收上下文供组合任务复用，组合任务仍调用语义层 helper。
- 组合任务遇到来源路由时，优先用局部分派表把来源映射到已绑定上下文的语义函数；不要为简单路由新增抽象 helper，也不要在主线里展开多段 `if/else`。
- 当需求要求逐项处理再汇总时，优先保持逐项映射的任务主线；去重、批量化、缓存等优化应在不改变任务判断结构的前提下引入。

## Python 原生结构

- Python 的推导式、生成器表达式和异步推导式有时比 `pipe` 更具可读性；当它们能更直接表达索引、集合、计数、存在性或简单筛选关系时，优先使用。
- 短推导式可采用单行形式；长推导式按 `1+3+1` 结构换行：

```python
items = [
    transform(x)
    for x in xs
    if keep(x)
]
```

- 生成器函数适合连续产出和延迟计算，优先让调用方决定何时求值。
- 普通 `for` 循环只在状态推进、早停、副作用分支清晰时使用。

## CLI

- 涉及 CLI 时，倾向用 `fire` 暴露 `main(...)`。
- `fire` 的具体参数设计、嵌套命令和返回值约定按具体任务确定，本文不预设。
- 如果任务明显需要更强的 CLI 交互、补全、复杂帮助文本或类型化命令结构，可以先讨论是否改用其他库。
